## 3. Modules and dependencies

Each package has its own `Package.swift` under `Packages/<Name>`.

| Module | Depends on |
| --- | --- |
| KeyboardCore, LayoutKit, SkinKit, QuickContentKit | none |
| CandidateKit | KeyboardCore, LayoutKit |
| AppearanceKit | SkinKit, CandidateKit |
| PackageManager | ZIPFoundation, Yams, KeyboardCore |
| RimeBridge | `RimeKit` (binaryTarget, `Vendored/RimeKit.xcframework`), `RimeLeversSupport` |
| RimeLeversSupport | `RimeKit` |

`RimeLeversSupport` ([sources](Packages/RimeBridge/Sources/RimeLeversSupport)) is a C target inside the RimeBridge package that forwards librime's levers API (`rls_available`, `rls_prepare_installation`, `rls_user_dict_list_*`, `rls_backup_user_dict`, `rls_restore_user_dict`) to Swift. It is compiled with `-fno-modules` against the original public headers, and booleans cross the boundary as explicit `int`. Outside Xcode, [build-learning-support.py](Tools/BuildRimeIOS/scripts/build-learning-support.py) builds its object file and module map from a `--kit-include-dir`.

### Engine artifact

- [RimeKitArtifact.json](Packages/RimeBridge/RimeKitArtifact.json) records the vendored engine: the artifact path, the generator and export scripts, the slices `ios-arm64` and `ios-arm64-simulator` with their archive path and SHA-256, and the files that pin the upstream commits ([VERSIONS.env](Tools/BuildRime/VERSIONS.env) and the plugin `*-VERSIONS.env` files in [Tools/BuildRimeIOS](Tools/BuildRimeIOS)).
- `Packages/*/Vendored/` content is produced by [Tools/BuildRimeIOS](Tools/BuildRimeIOS): [43-build-rimekit.py](Tools/BuildRimeIOS/scripts/43-build-rimekit.py) rebuilds librime and plugins from pinned sources (plugin sources fetched by [09-fetch-plugins.sh](Tools/BuildRimeIOS/scripts/09-fetch-plugins.sh)) with `-ffile-prefix-map`, and [export-rimekit.py](Tools/BuildRimeIOS/scripts/export-rimekit.py) checks the archives (required engine entry points, no absolute build paths), copies them into `Vendored/` and rewrites the manifest. `export-rimekit.py --check` re-verifies the installed copy and runs in `make release`.
- Components initialised by the bridge: `default`, `levers`, `lua`, `octagram`, `t9_original`, `predict`. Deployment preflight asks the live engine (`rb_component_available`); a scheme that needs a missing component is skipped with a warning.
- Native nine-key processor: [rime_t9_processor.cc](Tools/BuildRimeIOS/src/rime_t9_processor.cc) and [rime_t9_keys.h](Tools/BuildRimeIOS/src/rime_t9_keys.h). Digits 2-9 (including the physical keypad) are handed to librime's `Speller` with the scheme's own digit prism; modifier keys, ASCII mode and other keys pass through. The built-in 9-key companions (`keyboard_*_9.schema.yaml` in [Resources/BuiltinPackages/Basic](Resources/BuiltinPackages/Basic)) do not list the processor.
- Prediction after commit uses upstream [librime-predict](https://github.com/rime/librime-predict) (pinned in [PREDICT-VERSIONS.env](Tools/BuildRimeIOS/PREDICT-VERSIONS.env)). The app neither bundles nor downloads a predict database; the user imports one (header `Rime::Predict/` is validated).
- librime patches in [Tools/BuildRimeIOS/patches](Tools/BuildRimeIOS/patches), applied in name order: [librime-resource-id-confinement.patch](Tools/BuildRimeIOS/patches/librime-resource-id-confinement.patch) makes the resource resolvers refuse ids that are absolute or contain a `..` component, a backslash or a NUL (a schema naming `user_dict: /elsewhere` or `dictionary: ../x` would otherwise read or write outside the data folders); the refused id resolves to a missing path, so the lookup fails. [38-resource-id-harness.sh](Tools/BuildRimeIOS/scripts/38-resource-id-harness.sh) checks it against the pinned sources; [librime-table-build-remap.patch](Tools/BuildRimeIOS/patches/librime-table-build-remap.patch) re-reads the table pointers after the string-table allocation grows and remaps the file (tiny dictionaries crashed the build); [librime-tsv-write-failures.patch](Tools/BuildRimeIOS/patches/librime-tsv-write-failures.patch) makes the user-dictionary TSV writer report stream errors.

Key views are [WeightedKeyRow.swift](Apps/SharedKeyboard/WeightedKeyRow.swift), [AlternateCharacterKey.swift](Apps/SharedKeyboard/AlternateCharacterKey.swift) (alternates popup in [AlternateCharacterKey+Popup.swift](Apps/SharedKeyboard/AlternateCharacterKey+Popup.swift)), [KeyboardControlKeys.swift](Apps/SharedKeyboard/KeyboardControlKeys.swift), [KeyCalloutView.swift](Apps/SharedKeyboard/KeyCalloutView.swift) and [StableKeyboardControls.swift](Apps/SharedKeyboard/StableKeyboardControls.swift); their control layout is driven by `KeyboardControlPolicy` and `PhoneKeypadRailPolicy`. Long-press alternates come from `AlternateKeyPolicy` (nine-key digit keys and the first key use their layout-declared alternates instead); symbol pages use `SymbolPageTable` ([SymbolPageTable.swift](Apps/SharedKeyboard/SymbolPageTable.swift)). The shared character-key entry supplies the configured flick behavior for row pages, while explicit layout decisions override it. Ordinary alternate lists use the callout shape and shadow; each held list owns its surface, and only presentation geometry animates while drag picking uses final coordinates. Automatic control titles follow the cached input language and VoiceOver wording follows the app language; custom and legacy stored space titles remain authored. The nine-key bottom row in simplified Chinese is 123 | 中/英 | 空格 | 符 (`KeyboardControlPolicy.isBundledPhonePad`), with a wide space bar and long press on the symbol-page key typing 0; its symbol-page key, and #+= on the 123 page of the 14-, 18- and 26-key layouts, open one categorised symbol page: 常用, 最近, 中文, 英文 and 括号, then the symbol library's sets, read through `SymbolLibraryModel`. It always opens on 常用 and goes back to the typing page after one symbol unless 锁定 is on (session-only, never stored). On the 14-, 18- and 26-key layouts the 123 and row-shaped symbol pages put the 123/符号 switch in the Shift position of their third row (10 / 10 / switch + 7 marks + ⌫); the native row footer places a comma left of space (、 for Japanese, ， for Chinese) and 。 to its right; ASCII branches retain their existing punctuation. Authored footers keep their declared keys. Untouched bundled letter menus use the input script’s quotes and marks, including Japanese ・ー～; authored menus, including empty lists, stay explicit. The nine-key first-key punctuation cycle is `T9PunctuationCycle` (repeat taps within 0.8 s replace the previous symbol while the text anchor and commit generation match).

Keyboard pages live in LayoutKit: [KeyboardPageDefinition.swift](Packages/LayoutKit/Sources/LayoutKit/KeyboardPageDefinition.swift), [KeyboardPageCategory.swift](Packages/LayoutKit/Sources/LayoutKit/KeyboardPageCategory.swift) and [KeyboardPagePresets.swift](Packages/LayoutKit/Sources/LayoutKit/KeyboardPagePresets.swift) describe them, [KeyboardPageChrome.swift](Packages/LayoutKit/Sources/LayoutKit/KeyboardPageChrome.swift) holds authored bottom and side keys, and [KeyboardComposition.swift](Packages/LayoutKit/Sources/LayoutKit/KeyboardComposition.swift) picks the main, 123, symbol and ABC pages for each input method × layout. [KeyboardPageMarkCoverage.swift](Packages/LayoutKit/Sources/LayoutKit/KeyboardPageMarkCoverage.swift) finds the everyday 123 marks a pairing types on no page; the built-in symbol page takes them over. Editing logic is in [KeyboardPageKeyPath.swift](Packages/LayoutKit/Sources/LayoutKit/KeyboardPageKeyPath.swift), [KeyboardPageEditing.swift](Packages/LayoutKit/Sources/LayoutKit/KeyboardPageEditing.swift) and [LayoutKeyFaceEditing.swift](Packages/LayoutKit/Sources/LayoutKit/LayoutKeyFaceEditing.swift). Split settings are in [LayoutSplitConfiguration.swift](Packages/LayoutKit/Sources/LayoutKit/LayoutSplitConfiguration.swift); a layout's split may carry its own keys, `halves` (one `left`/`right` pair per layout row, written only once edited, absent otherwise), which replace the rows cut at `rowBreaks` while the keyboard is split. [SplitLetterPage.swift](Packages/LayoutKit/Sources/LayoutKit/SplitLetterPage.swift) dresses them as the Chinese letters page (Shift, Delete, footer), [SplitHalvesGeometry.swift](Packages/LayoutKit/Sources/LayoutKit/SplitHalvesGeometry.swift) solves one key width and one gutter for the widest cut row, and [SplitArrangementEditing.swift](Packages/LayoutKit/Sources/LayoutKit/SplitArrangementEditing.swift) holds the editor's draft edits (`SplitArrangementEditor` in [KeyboardRowsEditor.swift](Apps/HostApp/KeyboardRowsEditor.swift) is the split view). Pages never carry halves and the shape recognisers read the whole rows only; row, category, rail and footer geometry is in [StandardKeyRowGeometry.swift](Packages/LayoutKit/Sources/LayoutKit/StandardKeyRowGeometry.swift), [SplitSpaceRowGeometry.swift](Packages/LayoutKit/Sources/LayoutKit/SplitSpaceRowGeometry.swift), [KeyboardPageRowGeometry.swift](Packages/LayoutKit/Sources/LayoutKit/KeyboardPageRowGeometry.swift), [KeyboardCategoryRowGeometry.swift](Packages/LayoutKit/Sources/LayoutKit/KeyboardCategoryRowGeometry.swift), [KeyboardPageRailGeometry.swift](Packages/LayoutKit/Sources/LayoutKit/KeyboardPageRailGeometry.swift) and [KeyboardPageFooterGeometry.swift](Packages/LayoutKit/Sources/LayoutKit/KeyboardPageFooterGeometry.swift). [BuiltinLayouts.swift](Packages/LayoutKit/Sources/LayoutKit/BuiltinLayouts.swift) recognizes preset geometry and native footers; identity stays in `LayoutDefinitionIdentity`.

At runtime [KeyboardPanelView+Pages.swift](Apps/SharedKeyboard/KeyboardPanelView+Pages.swift) resolves pages (no key-path disk I/O) and keeps the panel-local symbol-language choice. Authored pages are drawn by [KeyboardAuthoredPageView.swift](Apps/SharedKeyboard/KeyboardAuthoredPageView.swift) and [KeyboardAuthoredPageChrome.swift](Apps/SharedKeyboard/KeyboardAuthoredPageChrome.swift); the key-area views are in [KeyboardKeyAreaViews.swift](Apps/SharedKeyboard/KeyboardKeyAreaViews.swift) and the shell, split, width and control-row decisions in [KeyboardPanelRules.swift](Apps/SharedKeyboard/KeyboardPanelRules.swift). Host previews ([KeyboardPreviewView.swift](Apps/SharedKeyboard/KeyboardPreviewView.swift), [KeyboardPagePreviewView.swift](Apps/SharedKeyboard/KeyboardPagePreviewView.swift)) reuse those views and rules.

Symbol previews follow the selected draft composition, including its main layout, missing everyday marks and native footer. `KeyboardPageResolver.symbolPresentation` chooses rows or categories for both rendering and editing. Copies of native symbol rows retain the comma before space and the `symbolLibrary` action (更多); unchanged native symbol footers retain the runtime widths. Previews resolve geometry at the hosting window's keyboard width, then scale the complete surface into their card, so form padding does not change footer slots or split decisions. [SymbolPageTable.swift](Apps/SharedKeyboard/SymbolPageTable.swift) supplies the same long-press hints to the panel and preview. [test_keyboard_page_preview.py](Tests/IOS/test_keyboard_page_preview.py) compares real UIKit key frames on an explicitly selected isolated simulator, using [KeyboardPagePreviewProbe.swift](Tests/IOS/Fixtures/KeyboardPagePreviewProbe.swift).

The globe-key requirement is checked by [InputModeSwitchKeyRequirement.swift](Packages/LayoutKit/Sources/LayoutKit/InputModeSwitchKeyRequirement.swift) when main layouts are saved, imported or selected in a pairing; auxiliary English, numeric and symbol pages may omit the globe and remain active as authored. The extension records the real requirement in [KeyboardSystemRequirements.swift](Apps/SharedKeyboard/KeyboardSystemRequirements.swift) and the host reads it on `HostConfigIOQueue`. Wide-surface content widths and docking come from [KeyboardWideContentPolicy.swift](Packages/CandidateKit/Sources/CandidateKit/KeyboardWideContentPolicy.swift).

Authored main-layout and auxiliary-page footers share automatic sizing in [KeyboardPageFooterGeometry.swift](Packages/LayoutKit/Sources/LayoutKit/KeyboardPageFooterGeometry.swift): ordinary keys keep a common width, Return keeps a wider target, and space takes the remainder. The visible keys determine this budget, independent of page, language and globe availability. Explicit widths retain relative-weight sizing, railed/keypad pages retain column alignment, and crowded rows scroll rather than shrink touch targets. Both split renderers use the same compact control budget.

Candidate presses pass through `CandidateAreaActionSink.prepare` in [KeyboardCandidateActions.swift](Apps/SharedKeyboard/KeyboardCandidateActions.swift). At touch-down, `KeyRollover` first commits any preceding letter whose finger is still held, then [InputSession+CandidateSelection.swift](Packages/KeyboardCore/Sources/KeyboardCore/Session/InputSession+CandidateSelection.swift) settles preceding code keys and binds the current candidate slot to a `PreparedCandidateSelection`; it does not select anything yet. This prevents a render-time A callback from rejecting a tap when the final letter has replaced the menu with B. On a valid release, the prepared word/context is selected synchronously in `touchesEnded`; the command is consumed exactly once before changing recognizer state, so UIKit failure dependencies or a reset before deferred target delivery cannot drop it; subsequent re-ranking resolves that same word, while a disappeared word, clear, previous selection or new composition invalidates the held press. [CandidateTouchTracking.swift](Packages/CandidateKit/Sources/CandidateKit/CandidateTouchTracking.swift) tracks candidate presses on the stable UIKit scroll container, so removing or recycling the original cell does not drop the release. Its observation is non-exclusive in both directions (`canPrevent` and `canBePrevented` return false): a non-cancelling ancestor tap recognizer cannot steal candidate selection. It confirms within a 10pt movement tolerance in window coordinates and discards the prepared action on real drags, system cancellation or removal of the whole candidate area. Small finger drift gets the same tolerance at cell edges as at the center; resizing during decoding or loading is not finger movement. [CandidateTouchFeedback.swift](Packages/CandidateKit/Sources/CandidateKit/CandidateTouchFeedback.swift) preserves immediate press feedback and accessibility; the release confirmation flash and haptic require an acknowledged host commit or real partial conversion progress. An unchanged engine result or a refused commit reports failure.

## 7. Data flows

### Engine and concurrency

- The Rime engine is a process-wide singleton. Creation, start and teardown go through `EngineOwnershipCoordinator` and `EngineOpQueue` ([EngineOpQueue.swift](Apps/SharedKeyboard/EngineOpQueue.swift)), both in [Apps/SharedKeyboard](Apps/SharedKeyboard); engine operations run on that serial queue. Host and extension are separate processes with separate engine instances.
- Reads of `active.json`, layouts and appearance go through `KeyboardResourceReadQueue` ([KeyboardResourceReadQueue.swift](Apps/SharedKeyboard/KeyboardResourceReadQueue.swift)); the main thread does not read disk synchronously. Imports use bounded same-descriptor reads that reject FIFOs and symlinks (`BoundedLocalFile`, `QuickContentFileReader`, `LayoutResourceBudget`).
- When a capability cannot be proven, the code fails closed and falls back to native Rime behavior.
- Candidate ranking and segmentation belong to the engine. The front end does not re-rank.
- The nine-key preedit shows letters for every key press (`ni'hao'y'y`) and is display-only; the committed text always comes from the engine (`SentenceSpelling`).

### Keyboard height

Keyboard height starts from the last accepted definition and appearance hint (`KeyboardInitialPresentation`) before the first frame. `KeyboardViewController` keeps UIKit's default registered root (`UIInputView`, default sizing) and changes its standard required height constraint; the existing `FeedbackInputView` and SwiftUI hosting view remain content children. Accepted physical-layout reports and appearance reads update `ExtensionPresentationStatus.budget` through the same controller path as orientation changes, without replacing the input controller or engine. Temporary pages and candidate/composition changes keep the current definition's budget. The physical main-row count shares the selected height preset's existing key-area budget; temporary ABC and numeric pages report their drawn-row count to fit that same shell. The formula is `KeyboardPanelPresentationBudget` / `presentationShellHeight` in [KeyboardPanelGeometry.swift](Packages/CandidateKit/Sources/CandidateKit/KeyboardPanelGeometry.swift); `KeyboardPanelHeightState` in [KeyboardPanelSizing.swift](Packages/CandidateKit/Sources/CandidateKit/KeyboardPanelSizing.swift) rejects stale presentation receipts and retains the nominal request separately from the viewport cap. On a phone with compact vertical traits in landscape, the root request and hosted content are capped at 50% of actual scene height after safe-area insets, leaving room for the system-owned strip outside the root. Scene geometry supplies the cap, never keyboard root bounds. Resource reads remain on `KeyboardResourceReadQueue`; budget updates run only for accepted size-changing configuration or geometry events.

### 7.1 Learning backup and merge

The user database (`userdb`) is private to the extension process, so the host submits a request and the extension executes it inside an exclusive-engine window. Backups use librime levers `backup_user_dict` / `restore_user_dict` (`.userdb.txt` snapshots); `export_user_dict` / `import_user_dict` exchange word lists and do not keep decay, tick or deletions. The live LevelDB is never copied.

Fixed slots live under `KeyboardLearning/` in the App Group container (`Slot` in [LearningTransferStore.swift](Packages/KeyboardCore/Sources/KeyboardCore/Support/LearningTransferStore.swift)):

| Slot | Content |
| --- | --- |
| `current.json` | the single authoritative state (<= 16 KiB): id, operation (`backup`/`restore`), status, source identity, `processID` (the execution lease identity), message, `hasSafetyBackup` |
| `restore-input.json` | archive carried by a restore request (written before `current.json`) |
| `backup-output.json` | archive produced by a backup request (written before status `succeeded`) |
| `safety-backup.json` | backup taken before a merge; kept across requests until the next real overwrite |
| `.lock` | short-held cross-process flock guarding state read-modify-write |
| `.worker-lock` | long-held execution lease |

Protocol:

- States: `pending -> running -> succeeded | failed`, plus `cancelled` (only from pending) and `interrupted` (a stale `running` recovered under a new lease). Cancel and claim are mutually exclusive under one flock. A submit never overwrites pending or running.
- Executor writes are compare-and-set on request UUID, `running` and the lease id. Late receipts from an old request or lease are rejected.
- Slot writes are atomic renames; `read()` takes no lock.
- Visibility is checked once per poll and Full Access once per attempt. Just before stopping the keyboard, `EngineOwnershipCoordinator.withExclusive(beforeYield:)` checks controller, resource identity and idle input; the request is claimed only inside the exclusive section.
- Archives ([LearningBackupArchive.swift](Packages/KeyboardCore/Sources/KeyboardCore/Support/LearningBackupArchive.swift)) must have `version` 1 and `producer` `keyboard-extension`; at most 32 dictionaries, each <= 4 MiB, 8 MiB raw in total, 12 MiB encoded; digests are 64-char lowercase hex and checked against the data. Decoding is incremental and rejects the 33rd dictionary before parsing it.
- Merge requires the same source and resource revision, dictionary names matching the engine's declared set and `rime_version`, and a successfully saved safety backup (`completeRestore` enforces it). The merge is librime's own `restore_user_dict`; results are not re-read or re-checked. It is not atomic and not rolled back; `.mergeUnverified` is thrown only after a native write was attempted. The safety backup is for retention and inspection, not rollback.
- [RimeLearningBackup.swift](Packages/RimeBridge/Sources/RimeBridge/RimeLearningBackup.swift) checks imported snapshots only for header, `db_name`, `db_type`, `user_id`, `rime_version` and size caps (32 files, 4 MiB each, 8 MiB total); rows are left to librime. A backup sets the previous `.userdb.txt` in the sync folder aside as `.userdb.txt.prior` and puts it back if the backup fails.
- Import of snapshots from other Rime front-ends (Squirrel, Weasel, Trime, fcitx5-rime, Hamster): the host picks one file (recognised by its content), a ZIP or a folder. [RimeSnapshotCollector.swift](Packages/KeyboardCore/Sources/KeyboardCore/Support/RimeSnapshotCollector.swift) takes only `*.userdb.txt` inside a ZIP ([BoundedZipReader.swift](Packages/KeyboardCore/Sources/KeyboardCore/Support/BoundedZipReader.swift): stored and deflate entries, no ZIP64 or encryption) or a folder, skips `__MACOSX` and hidden files, goes at most 3 levels deep, and keeps the archive's caps (32 files, 4 MiB each, 8 MiB total; a larger pick is refused whole). [RimeUserDbText.swift](Packages/KeyboardCore/Sources/KeyboardCore/Support/RimeUserDbText.swift) needs `/db_name` (a `.userdb…` suffix is stripped like librime's `GetDbName`), accepts a missing `/db_type`, `/rime_version` and `/user_id`, CR LF and a BOM, and refuses non-UTF-8 text. The snapshots travel as a restore request whose archive has producer `rime-userdb-import`, the only producer that may repeat a dictionary name (one snapshot per installation). In the extension, `planImportedLearningData` keeps the snapshots for dictionaries the input scheme in use declares; without a match the request fails before the safety backup. Otherwise the same safety backup runs, `restoreImportedLearningData` merges each snapshot with librime's restore (higher commit count and weight win, nothing is deleted), and the success receipt carries the result line.
- An empty producer list fails; a fresh empty `userdb` (tick 0, no entries) is a valid payload.

### Complete configuration backups

The host's **备份与恢复** page contains complete iCloud/local backups and the existing per-source learning transfer controls. `ConfigurationBackupModel` schedules changed configurations while the app is active (at least five minutes between automatic archives), registers an opportunistic `BGProcessingTask`, and lists iCloud metadata, including actual upload state. It uses the private `iCloud.app.songyan.ime` Documents container; cloud synchronization is performed only by the host. New installations can enter the same restore page from onboarding. A completed local archive is handed to iCloud. Historical archives are not automatically deleted.

`ConfigurationBackupArchive` in PackageManager streams versioned ZIP archives through a private staging directory. Its manifest records allowlisted domains, relative paths, sizes and SHA-256 digests; identical resource contents share one compressed blob within each archive. Capture refuses concurrent source changes, symlinks and live Rime user databases; restore validates the entire archive before touching live configuration. Version 2 backs up Rime overrides, layouts and page compositions, symbols, quick content, appearance, hints, options, keyboard preferences and exported learning snapshots. `ConfigurationBackupDependencies` records scheme identity, source URL or Rime source expression, recipe arguments, effective custom patches, model size/hash/download address and the desired keyboard roster/selection. Scheme bodies, bundled or generated dictionaries, compiled builds, published resource copies and grammar models are excluded. Network dictionaries are references; original locally imported dictionary sources are retained. Model download provenance survives both plain imports and recipe installations. Device permissions and diagnostics are excluded. Version 1 archives remain readable.

`ConfigurationRestoreTransaction` prepares replacements beside their destinations and journals the commit. The next app launch rolls back an interrupted commit before loading managers. Existing immutable publication generations remain available to running keyboards. Version 1 restores commit `active.json` last under the publication lock. Version 2 restores commit portable intent, then `ConfigurationDependencyRestorer` resolves local/bundled/HTTPS sources, verifies model and dictionary hashes, reinstalls through normal deployment validation and republishes the recorded keyboards with new generation IDs. It never installs an old activation marker without its resources. Failures stay in a persistent retry list and remain represented in later backups; the selected source is applied last. A separate local complete archive is kept before each restore. The learning worker lease excludes an in-progress merge during restoration.

`LearningSnapshotStore` retains text exports per source and resource revision, independent of the manual transfer slot. The extension requests an export when idle, at most once per 15 minutes per source, when automatic backup and Full Access are enabled. The UI shows the snapshots actually collected, without claiming unsaved live database contents are in the archive. After the user confirms a complete restore, matching snapshots are merged through the existing exclusive-engine transfer path when each source is used. After a dependency is verified and rebuilt, only its newest unsubmitted snapshot is retargeted to the new revision. Failed/interrupted merges are not automatically replayed. A successful empty engine export is recorded as an empty safety checkpoint so a fresh installation can restore learning data.

Verification: PackageManager archive/rollback tests, KeyboardCore snapshot/transfer tests, and `Tests/IOS/test_configuration_backup.py` on an isolated simulator exercise archive compatibility, resource exclusion, configuration round trips, dependency regeneration, custom page/selection retention, scoped deletion and deferred learning restoration.
